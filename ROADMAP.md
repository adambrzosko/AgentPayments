# Roadmap to Production

Prioritized list of work required before real websites can rely on AgentPayments. Ordered by severity: P0 = exploitable today, P1 = adoption blocker, P2 = quality/scale.

## P0 — Security fixes (gate is currently bypassable)

### 1. Challenge bypass via faked headers — **mitigated**
`isBrowser()` only checks for `Sec-Fetch-Mode`/`Sec-Fetch-Dest`, which any HTTP client can set, and the verify endpoint accepted any `fp` ≥ 10 chars. Fixed: SHA-256 proof-of-work (default ~65k hashes per cookie, configurable), base64 fingerprint validation server-side, single-use nonces, and nonce/cookie binding to client IP. See SECURITY.md. Remaining: a determined attacker with native code can still solve PoW cheaply — raising difficulty, TLS/JA3 fingerprinting, or behavioral signals would be the next escalation.

### 2. Payment verification accepts non-payments — **fixed**
`verifyPaymentOnChain` accepted any `spl-token` `transfer` ≥ 0.01 of *any* token to *any* destination, in any transaction that merely referenced the vendor wallet. Fixed: payment now must land in one of the vendor's USDC token accounts, with the mint re-checked for `transferChecked`. Further hardened across all three SDKs (`sdk/node`, `sdk/edge`, `sdk/python`): the paid amount is now read from `meta.preTokenBalances`/`meta.postTokenBalances` (the actual balance change on the vendor's — and fee wallet's — USDC token account) instead of parsing a specific `transfer`/`transferChecked` instruction. This is token-program-agnostic by construction (works identically for legacy SPL Token, Token-2022, or any future program, sidestepping an unverified assumption about whether every RPC provider labels Token-2022 instructions consistently), robust to arbitrarily-nested CPI transfers (no dependence on `innerInstructions` depth), and correctly reflects fee-on-transfer token extensions (measures what the vendor actually received, not what an instruction claims was sent). `accountIndex` resolution correctly handles both an account created in the same transaction (no `preTokenBalances` entry — treated as a 0 pre-balance, not skipped) and versioned transactions with address-lookup-table accounts. The memo check (proving the payment references this specific agent key) is unchanged — memo instructions have no balance signature to diff. `verifyPaymentOnChain`'s public boolean-returning signature is untouched; only the internal `_scanForPayment`/`_scan_for_payment` amount-resolution logic changed. Remaining hardening: check commitment level (finalized vs. confirmed) — already using `finalized` everywhere, this is about explicitly re-validating it rather than trusting the RPC response's implicit guarantee.

### 3. Cookies are not bound to a client — **fixed**
A verification cookie was `timestamp.hmac` — identical for every visitor, valid from any IP. Now the cookie HMAC includes a client-IP hash, so a captured cookie fails from any other IP. Trade-off: clients whose IP changes mid-session re-solve the challenge.

### 4. RPC exhaustion DoS on the agent path — **fixed**
Valid agent keys are free to mint (every 402 issues one) and each unpaid key triggered up to ~100+ `getTransaction` calls. Fixed: negative results cached 30 s (skips RPC on repeated attempts), agent-key verification path rate-limited at 10 req/min/IP, and `getTransaction` calls capped at 20 per verification. Remaining: negative results on the KV store propagate across isolates via the pluggable store interface, but the in-memory fallback is still per-isolate.

### 5. Paid access silently expires — **fixed**
Verification re-scans the last 100 signatures, so a paid key stopped working once the wallet received 100 newer transactions. Fixed: pluggable `grantStore` interface (Node: `sdk/node/grant-store.js`, Python: `sdk/python/agentpayments_python/grant_store.py`). Once a key is verified it is added to the store and never re-scanned. Default is in-memory (no persistence). `FileGrantStore` writes to a JSON file with atomic rename — survives restarts, not suitable for multi-process deployments. For multi-process use Redis or a database. Edge: the `CloudflareKVStore` already stores results durably with a 30-day TTL for positive results (set by `PAYMENT_CACHE_TTL` in `setCachedPayment`).

### 6. Nonce replay — **fixed (best-effort on edge)**
Nonces now carry a random component and are tracked in an in-memory consumed set after use. On multi-isolate edge runtimes this is per-isolate until a shared state backend lands (see P1).

### 7. Private keys committed to git — **fixed**
`jsons/wallet-keys.json` and `jsons/bot-wallet.json` were tracked in git; `jsons/` is now gitignored so no new keys get committed. History has been purged: `git filter-repo --path jsons/ --invert-paths` run against a mirror clone, force-pushed to `main`/`onchain-platform-fee`/`testsAndImprovements` on the public repo, verified zero commits reference `jsons/` anywhere in the pushed history. The devnet keys that were exposed should still be treated as compromised — history rewriting stops future exposure, it doesn't erase any copy already scraped/cloned before the purge.

## P1 — Adoption blockers

### SEO safety (the #1 objection from prospective sites) — **fixed**
Search crawlers received a 402 like any other non-browser. Fixed: all three SDKs now run a verified-crawler check before the gate — UA pattern match followed by reverse+forward DNS verification (Google's documented method). Googlebot, Bingbot, Slurp, DuckDuckBot, Baiduspider, YandexBot, and Applebot are supported. Results are cached 1 hour. On by default; disable with `verifyCrawlers: false` (Node/Edge/Next/Flask/FastAPI) or `AGENTPAYMENTS_VERIFY_CRAWLERS = False` (Django). Remaining: IPv6 reverse DNS not yet supported in the edge DoH path.

### Legacy browser fallout — **fixed**
Browsers without `Sec-Fetch-*` headers (Chrome < 76, Firefox < 90, some mobile WebViews) got a 402. Fixed: `isBrowser` now falls back to a UA regex (Chrome, Chromium, Firefox, Safari, Edge, Opera, Samsung Browser, UC Browser) when Sec-Fetch headers are absent, with an explicit bot-UA exclusion to stop scrapers spoofing a browser UA.

### Pluggable state backends — **fixed (Node, Edge, Python)**
Rate limiter and payment cache are in-memory by default — per-process on Node (e.g. `gunicorn -w 4`/PM2 cluster mode gives each process its own state), per-isolate on Cloudflare/Vercel/Netlify, so limits are effectively `N ×` too generous in aggregate and every process/isolate independently re-scans the chain for the same payment. Fixed:

- **Node** — `sdk/node/redis-store.js` provides `RateLimiter`, `PaymentCache`, and `createRedisStore(redisClient)`, backed by atomic Lua INCR+EXPIRE / SET EX. Pass via `rateLimiter`, `agentKeyRateLimiter`, `paymentCache` options to `agentPaymentsGate`.
- **Python** — was the bigger gap: the three rate limiters and the payment cache were hardcoded module-level singletons with **no way to plug in anything** (unlike Node, which already had `paymentCache`/`rateLimiter` options). Fixed: `verify_payment_on_chain`/`_scan_for_payment` now accept an optional `payment_cache` argument, and all three adapters accept `agent_key_rate_limiter`/`challenge_issue_rate_limiter`/`payment_cache` (plus a `challenge_verify_rate_limiter` on the separate `/__challenge/verify` endpoint, which lives outside the main middleware). New `sdk/python/agentpayments_python/redis_store.py` mirrors Node's `redis-store.js` exactly (`RateLimiter`, `PaymentCache`, `create_redis_store(redis_client)`, same Lua-script atomicity, fail-open on errors) — duck-typed against any client exposing `eval`/`get`/`set`, no hard dependency on the `redis` package.
- **Edge** — `CloudflareKVStore` already existed for Cloudflare Workers (cross-isolate nonce/rate-limit/payment-cache via KV), but the platform convenience wrappers (`createAgentPaymentsWorker`, `createNetlifyGate`, `createVercelEdgeGate`) silently dropped several `createEdgeGate` options entirely — `store`/`getStore` weren't exposed on the Netlify/Vercel wrappers at all (so there was no way to plug in a durable backend even if you built one), and none of the three wrappers threaded through `accessDuration`/`pricingTiers`/`routes`/`verifyCrawlers`/`requireHttps` added for the pricing model. Fixed: all three wrappers now pass through the full option set. Netlify and Vercel still ship no built-in durable `Store` implementation (no KV-equivalent binding to auto-detect the way Cloudflare's is) — bring your own backed by Netlify Blobs, Vercel KV, Upstash Redis, etc.

### `isBrowser()` misclassifies fetch()-based agents as browsers — **fixed**
Discovered building the live demo (`demo/`): Node's built-in `fetch()` (undici) always sends `sec-fetch-mode: cors` on every request — not settable, not overridable via the `headers` option. `isBrowser()` in all three SDKs checked for the mere *presence* of `Sec-Fetch-Mode`/`Sec-Fetch-Dest` before falling back to the UA regex, on the documented assumption that only real browsers send these headers (true when that check was written — Chrome 76+/Firefox 90+). That assumption no longer held: any AI agent built on Node's `fetch()`, or any other spec-compliant HTTP client that sets Fetch Metadata headers, was served the interactive JS challenge page instead of the machine-readable 402 JSON — the agent had no way to proceed. Confirmed directly: a Node `fetch()` call with a clearly non-browser User-Agent still received the HTML challenge page (status 200), while the identical request via `curl` or `http.request` correctly received 402 JSON. Fixed in all three SDKs (`sdk/node`, `sdk/edge`, `sdk/python`): the Sec-Fetch signal now requires `Sec-Fetch-Mode: navigate` or `Sec-Fetch-Dest: document` specifically — values set exclusively for top-level navigations and not reachable through the fetch()/XHR APIs — rather than treating any Sec-Fetch header value (including `cors`) as browser-proof. Real browser navigations are unaffected (they always send `navigate`/`document`); in-page browser `fetch()`/XHR calls still fall through correctly to the existing UA-regex check. Test coverage added for both a real-browser-navigation request and a fetch()-shaped agent request (`sec-fetch-mode: cors`, no `Sec-Fetch-Dest`, non-browser UA) in each SDK's suite. Confirmed this was hitting real production agent traffic, not just a theoretical edge case: `langchain-core`'s shared `AsyncCaller.fetch()` calls the global `fetch()` directly, and both `openai-node` and `anthropic-sdk-typescript` (wrapped by `@langchain/openai`'s `ChatOpenAI` and `@langchain/anthropic`'s `ChatAnthropic`) default to `globalThis.fetch` with no way to opt out of the `Sec-Fetch-*` headers it sends — fetch() is the default, unavoidable transport for the two most widely-used LLM provider SDKs in the Node ecosystem, so this was a likely real contributor to the existing "ChatGPT and other LLM agents don't reliably read the 402 response instructions" issue in TODO.md, not just an artifact of the demo build.

### x402 protocol compatibility — **fixed**
LLM agents don't reliably parse the custom 402 JSON (noted in TODO). Fixed: all three SDKs (Node, Edge, Python) now emit `x402Version: 1`, `accepts: [PaymentRequirements]`, and an `X-PAYMENT-REQUIRED` base64-encoded header on every 402 response, following the x402 SVM `exact` scheme spec. Chain IDs use CAIP-2 format (`solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` mainnet, `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` devnet). Amount is in base units (micro-USDC). x402 utilities also exported from `agentpayments_python` (`build_payment_requirements`, `enrich_402_body`, `payment_required_header`).

### Production RPC strategy — **documented, paid RPC confirmed**
Public Solana endpoints heavily rate-limit `getSignaturesForAddress`/`getTransaction` — confirmed live this session (a burst of `getTransaction` calls during real devnet verification testing hit 429s against `api.devnet.solana.com`). Fixed by switching to [Helius](https://helius.dev): the same burst pattern (20 concurrent `getTransaction` calls against a heavily-used test wallet) returned all 200s against Helius's devnet endpoint. Recommended for anyone running AgentPayments in production — set `solanaRpcUrl`/`SOLANA_RPC_URL`/`solana_rpc_url` to your Helius endpoint (all three SDKs accept a string or array, so you can keep the public endpoint as a fallback: `[heliusUrl, 'https://api.devnet.solana.com']`). Remaining: add an optional webhook-based payment indexer so verification is a single lookup instead of a chain scan.

### Pricing & access model — **fixed (self-hosted gate)**
One 0.01 USDC payment used to buy indefinite access, with no way to configure price per route, expire it, or revoke it. Fixed across all three SDKs (`sdk/node`, `sdk/edge`, `sdk/python`):

- **Configurable price** — `minPayment` was already there for Node/Edge; Python was the gap (`verify_payment_on_chain` had no parameter at all, hardcoded from a module constant) — closed, threaded through all three Python adapters (`min_payment` kwarg / `AGENTPAYMENTS_MIN_PAYMENT` setting for Django).
- **Payment-amount → access-duration mapping** — new `accessDuration` (flat) and `pricingTiers` (`[{ minAmount, durationSeconds, name }]`) options. The gate finds the highest tier the actual on-chain amount clears and grants that tier's duration; non-floor tiers also appear as their own entries in the 402 response's x402 `accepts[]` array so an agent can compare price/duration tradeoffs upfront. `verifyPaymentOnChain`'s public boolean-returning signature is unchanged (existing tests untouched) — a new internal `_scanForPayment`/`_scan_for_payment` helper returns the actual amount paid for tier resolution.
- **Per-route pricing tiers** — new `routes: [{ pathPrefix, minPayment, accessDuration, pricingTiers }]` option, longest-prefix matched, so a single gate/middleware instance can price different paths differently (Express/Koa/Fastify users can still just mount multiple gate instances, as before).
- **Key revocation** — `MemoryGrantStore`/`FileGrantStore` (Node and Python) gained a `revoke(agentKey)` method; `has()` already returns false for a revoked or expired grant, so the gate's hot path needed no changes. Edge (which has no durable grant store by design) gets an analogous `invalidatePayment(agentKey)` on its `Store` interface that clears the payment cache, forcing re-verification.
- Edge's "access duration" is intentionally implemented differently from Node/Python: since Edge has no durable per-key store, a longer duration is expressed as a longer payment-cache TTL rather than a true persistent grant — documented as such, not papered over.
- On-disk `FileGrantStore` files written by older SDK versions (plain JSON arrays of key strings) still load correctly as permanent grants — no migration needed to upgrade.

Deferred, out of scope for this pass: hosted-platform (`agp_`) per-key pricing/revocation. Those keys are stateless HMAC tokens with no server-side record at all today — adding that would need a new `keys` table, endpoints, and dashboard UI on the hosted platform (`api/`), which is really its own project tied to the "Vendor UI" initiative already tracked separately.

### Publishing — **done**
`@agentpayments/node`, `@agentpayments/edge` (npm) and `agentpayments-python` (PyPI) are published at v0.1.0, verified installable from a clean environment with no monorepo context. `sdk/next` stays unpublished (`private: true`) until it's ready for real installs. Remaining: the packages' baked-in `PLATFORM_API_URL` default still points at the placeholder `api.agentpayments.dev` — the real hosted platform is now live at `api.agentpayments.cloud` (custom domain connected). A version bump + republish is needed for that to be the zero-config default; deferred for now, tracked in `TODO.md`.

## P2 — Quality and scale

- Vendor dashboard: payments received, keys issued/active, blocked-request stats (already in TODO).
- Proxy adapter (Nginx/Envoy) for non-Node/Python stacks.
- Structured logging for Python SDK (Node/Edge already have it).
- Configurable cookie lifetime and challenge difficulty.
